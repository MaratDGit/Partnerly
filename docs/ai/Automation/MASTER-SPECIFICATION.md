# PARTNERLY — UNIVERSAL AUTOMATION PLATFORM

## ГЛАВНАЯ ЦЕЛЬ

Я хочу создать внутри существующего проекта Partnerly полноценную универсальную платформу автоматизации процессов (Universal Automation Platform).

Это не просто Scheduler и не обычный Background Service.

Мне нужна система, которая позволит пользователям самостоятельно создавать практически любые автоматизированные процессы, настраивать их последовательность, условия выполнения, расписание и действия.

Система должна быть универсальной, расширяемой, независимой от конкретных бизнес-модулей Partnerly и пригодной для дальнейшего развития в отдельный SaaS-продукт.

`Automation/`

Ты самостоятельно должен спроектировать внутреннюю архитектуру этой папки.

Самостоятельно определи:

- Структуру каталогов.
- Количество и назначение классов.
- Интерфейсы.
- Модели.
- Сущности базы данных.
- Названия таблиц и полей.
- Связи между таблицами.
- Сервисы.
- Репозитории, если они необходимы.
- Механизмы выполнения.
- Механизмы планирования.
- Механизмы обработки событий.
- Механизмы хранения состояния.
- Механизмы регистрации компонентов.
- Способы интеграции с существующим Partnerly.

**Не используй заранее заданную структуру классов или таблиц. Разработай собственную архитектуру на основании анализа существующего проекта.**

Единственное обязательное ограничение: вся новая бизнес-логика Automation должна находиться внутри отдельной папки `Automation/`.

В существующие файлы Partnerly вноси только минимально необходимые изменения для интеграции нового модуля.

Не переноси существующие бизнес-модули внутрь Automation.

## 3. ВОЗМОЖНОСТИ AUTOMATION PLATFORM

Система должна поддерживать следующие возможности.

### A. Automation Management

Пользователь должен иметь возможность:

- Создавать автоматизации.
- Редактировать.
- Копировать.
- Удалять.
- Активировать.
- Деактивировать.
- Запускать вручную.
- Останавливать выполнение.
- Просматривать историю.
- Создавать версии.
- Сохранять черновики.
- Публиковать готовые автоматизации.

### B. Universal Triggers

Автоматизация должна запускаться различными способами:

- Manual Trigger.
- Scheduled Trigger.
- Time Interval Trigger.
- Entity Created.
- Entity Updated.
- Entity Deleted.
- Webhook Trigger.
- Event-Based Trigger.
- Delayed Trigger.

Архитектура должна позволять легко добавлять новые типы триггеров.

### C. Universal Conditions

Пользователь должен иметь возможность создавать условия:

- Equals.
- Not Equals.
- Greater Than.
- Less Than.
- Contains.
- Is Empty.
- Is Not Empty.
- Changed.
- AND.
- OR.
- NOT.
- Nested Conditions.

Условия должны поддерживать различные типы данных и вложенные комбинации.

### D. Universal Actions

Реализуй расширяемую систему действий.

В первоначальную версию включи:

- Send Email.
- Send Notification.
- Create Record.
- Update Record.
- Find Record.
- Delete Record, только при наличии соответствующих разрешений.
- Delay.
- Wait Until.
- Conditional Branch.
- Switch.
- Set Variable.
- HTTP Request.
- Webhook.
- Execute Workflow.

Возможность добавления новых Actions должна быть максимально простой.

Добавление нового Action не должно требовать переписывания основного Automation Engine.

### E. Workflow Execution

Система должна уметь выполнять сложные последовательности действий.

Поддержи:

- Последовательные действия.
- Условные ветвления.
- Несколько путей выполнения.
- Зависимости между шагами.
- Передачу результатов между шагами.
- Динамические переменные.
- Задержки.
- Повторные попытки.
- Таймауты.
- Отмену.
- Восстановление после перезапуска приложения.

Не ограничивай архитектуру простым списком последовательных действий. Предусмотри возможность развития до полноценного визуального Workflow Engine.

### F. Universal Scheduler

Создай надёжный Scheduler.

Поддержи:

- One Time.
- Every X Minutes.
- Hourly.
- Daily.
- Weekly.
- Monthly.
- Custom Cron.
- Specific Date.
- Event-Based Scheduling.
- Delayed Execution.

Обязательно учитывай TimeZone пользователя.

Пользовательские расписания должны сохраняться в SQL Server и переживать перезапуск приложения.

Исследуй возможность использования Hangfire или другой подходящей библиотеки, совместимой с .NET 6.

Самостоятельно выбери наиболее подходящую технологию и обоснуй решение.

### G. Execution History

Каждое выполнение должно иметь историю.

Пользователь должен видеть:

- Время запуска.
- Время завершения.
- Причину запуска.
- Общий статус.
- Выполненные действия.
- Результаты действий.
- Ошибки.
- Количество повторных попыток.
- Продолжительность выполнения.

Добавь возможность повторного запуска неудачных процессов с соблюдением идемпотентности.

### H. Dynamic Variables

Создай универсальную систему переменных.

Пользователь должен иметь возможность использовать:

- Данные триггера.
- Данные сущностей.
- Результаты предыдущих действий.
- Переменные текущего Workflow.
- Данные выполнения.
- Даты и время.

Например:

`{{user.email}}`

`{{ticket.status}}`

`{{execution.startedAt}}`

`{{steps.findUser.result}}`

Система должна валидировать переменные и контролировать доступ к данным.

## 4. UNIVERSAL ENTITY INTEGRATION

Одна из важнейших задач — сделать Automation независимой от конкретных таблиц Partnerly.

Не создавай отдельный механизм автоматизации для каждого модуля.

Разработай универсальный механизм подключения сущностей.

Он должен позволять регистрировать доступные сущности и предоставлять Automation информацию о:

- Названии сущности.
- Доступных полях.
- Типах данных.
- Поддерживаемых операциях.
- Разрешённых действиях.
- Ограничениях доступа.

В дальнейшем я должен иметь возможность подключить новую сущность Partnerly к Automation без изменения основного движка.

На первом этапе изучи существующие сущности Partnerly и подключи те, которые безопасно и целесообразно использовать.

Все операции с сущностями должны проходить через проверенные серверные механизмы доступа.

Не разрешай произвольное выполнение SQL или пользовательского C# кода.

## 5. VISUAL WORKFLOW BUILDER

Создай современный визуальный Workflow Builder.

Я хочу, чтобы пользователь мог самостоятельно создавать автоматизации, соединяя визуальные блоки.

Интерфейс должен поддерживать:

- Добавление Trigger.
- Добавление Action.
- Добавление Condition.
- Соединение блоков.
- Создание ветвлений.
- Настройку каждого блока.
- Перемещение блоков.
- Удаление блоков.
- Сохранение Workflow.
- Валидацию Workflow.
- Тестовый запуск.
- Публикацию.

Исследуй подходящие frontend-библиотеки, совместимые с существующим проектом.

Самостоятельно выбери оптимальный вариант.

Не создавай имитацию визуального конструктора в виде статичной картинки.

Это должен быть реальный работающий редактор.

Дизайн должен соответствовать Partnerly Premium SaaS UI.

Сохраняй текущие дизайн-токены, цвета, тему, адаптивность и общие UI-компоненты проекта.

- Google.

- Другие API.
- Webhooks.
- Внешние SaaS-платформы.

## 8. AI AUTOMATION — АРХИТЕКТУРНЫЙ ЗАПАС

Пока не реализуй полноценную AI-систему.

Но спроектируй Automation так, чтобы в будущем можно было добавить AI Assistant.

Пример будущего использования:

Пользователь пишет:

"Каждый понедельник проверяй пользователей, которые не заходили на сайт более 30 дней, и отправляй им напоминание."

AI должен будет преобразовать текст в готовый Workflow.

Предусмотри возможность программного создания, изменения, проверки и публикации Workflow через внутренние сервисы.

AI не должен иметь возможности обходить права доступа или самостоятельно выполнять незарегистрированный код.

## 9. MULTI-USER SECURITY

Система предназначена для многопользовательской платформы.

Обязательно обеспечь:

- Изоляцию данных по владельцам.
- Проверку UserId на сервере.
- Защиту от IDOR.
- Проверку Permissions.
- Защиту Webhook.
- Защиту API.
- Валидацию всех конфигураций.
- Контроль доступа к Entity Fields.
- Защиту от повторного выполнения.
- Ограничение количества запусков.
- Ограничение ресурсов.

Пользователь не должен иметь возможности запускать, читать, редактировать или отменять чужие автоматизации.

## 10. НАДЁЖНОСТЬ

Automation Engine должен быть рассчитан на длительную работу.

Обязательно продумай:

- Persistent Execution.
- Retry Policies.
- Idempotency.
- Concurrency Control.
- Distributed Execution.
- Execution Recovery.
- Timeouts.
- Cancellation.
- Error Handling.
- Versioning.
- Audit Logging.

Не используй длительный Task.Delay для ожидания часов или дней.

Не допускай ситуации, когда перезапуск Partnerly приводит к потере запланированных процессов.

Не выполняй длительные Workflow в HTTP Request жизненном цикле.

## 14. ПОРЯДОК РАБОТЫ

Не начинай сразу писать весь код.

Работай в следующем порядке:

### PHASE 1 — ANALYSIS

Изучи весь существующий Partnerly.

Ничего не изменяй.

Подготовь архитектурный анализ и рекомендации.

### PHASE 2 — ARCHITECTURE DESIGN

Самостоятельно спроектируй внутреннюю архитектуру папки Automation.

Определи все необходимые компоненты, сущности, связи и зависимости.

Подготовь документацию архитектуры.

### PHASE 3 — CORE IMPLEMENTATION

Создай основное ядро Automation Engine.

Реализуй Registry, Triggers, Conditions, Actions и Workflow Execution.

### PHASE 4 — DATABASE & SCHEDULER

Реализуй хранение данных, миграции и Scheduler.

### PHASE 5 — PARTNERLY INTEGRATION

Подключи существующие сервисы, сущности, авторизацию, Notifications, Email и SignalR.

### PHASE 6 — USER INTERFACE

Создай Dashboard, Automation Management и Visual Workflow Builder.

### PHASE 7 — SECURITY & TESTING

Выполни тестирование, аудит безопасности и исправление ошибок.

### PHASE 8 — FINAL REVIEW

Подготовь документацию и финальный отчёт.
